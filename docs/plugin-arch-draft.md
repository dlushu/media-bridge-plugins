## 一、范围与验收判据

**这套改动只改架构，不改行为。** 验收判据：改完之后，现有全部功能与输出保持不变，
可用现有方式回归验证。做不到这一条，说明改动顺手改了行为，应停下。

## 二、已确定

### 2.1 插件的身份与目录

- 插件按**类型**分组；身份 = `(类型, 插件 id)`。同一个 `id` 在不同类型下是两个插件，互不冲突。
- 目录布局（都在数据目录下）：

  ```
  plugins/<类型>/<插件 id>/         包本体（代码 + 自带 webui 静态文件 + 设置字段声明）
  plugins/<类型>/<插件 id>/data/    插件自己的数据目录
  ```

  ⚠️ 具体路径以实现为准。现状是：源的包在 `sources/`、清单在 `sources.json`，
  `plugins/` 是把这套推广到多类型。

- 类型：`metadata`（元数据）、`source`（源）、`home`（首页插件，从 emby 侧搬入统一插件树）。
- **已定 1（选 B）**：所有插件进统一插件树，并**新增一个插件管理页**（安装 / 卸载 / 启停 / 状态可见）。
- **已定 24：包与校验**。插件包 = **一个 tar.gz**，解到 `plugins/<类型>/<id>/`；
  校验**复用现有的两道 md5**（源包已经是这个做法，见 ADR-0015）；
  插件清单里写 `version` 与"依赖的域 / 其他插件"，**缺依赖时如实失败并点名缺哪个**。

### 2.2 元数据插件与源插件的关系

- 两者是**两个独立的插件**：各自安装、卸载、升级，互相不感知。
- **面板层是唯一的连接点**：元数据插件注册**域 id**（= 条目 Id 的前缀），
  面板按域名把"条目 → 模板 → 源"连起来。

### 2.3 职责切分

- 面板定义**公共端点**与**规范字段**；插件按自己的协议取数，并**归一化成规范字段**返回。
- 面板只做两件事：① 编辑请求参数；② 把规范字段转成 Emby DTO。
- 打分、条数、线路过滤留在面板侧（聚合层）—— 这三项是"挑哪一条"，与取数协议无关。
- `init`（首次搜索前的预热）**不属于公共端点**：面板只发"搜索"，插件自行决定是否预热。

### 2.4 webui

- 插件的 webui 是**静态文件**，放在插件包里、由面板托管；**插件不提供端口**。
- **两个层级必须分开**（早先的描述把二者混为一谈，此处校正）：

  | 层级 | 是谁的东西 | 内容 | 现状对应 |
  |---|---|---|---|
  | **插件设置页** | 插件 | 管理它自己的实例：添加 / 启动 / 停止 / 删除 / 自动更新 | 现有源托管的「猫源地址」页 |
  | **实例配置中心** | 实例 | 那个实例自己的配置界面 | 现有每个「配置中心」（`/website`） |

  ⇒ 导航上**不再给每个运行中的实例单独开一个子页**（现状是跑起来几个源就有几个「配置中心」），
  而是**收进插件的设置页内部**（从那里点进某个实例）。
- 导航上：「元数据」一栏，下面挂各已注册元数据插件的设置页。
- 面板设置页里现有的上游配置卡，改为元数据插件自带的设置。

### 2.5 归一化与 Emby

- 插件返回规范字段；面板把规范字段转成 Emby DTO 与客户端交互。
- "坐标 ↔ 元数据"的细节由元数据插件自己决定（返回什么由它定），但必须按规范给出面板需要的
  字段，并**申报能力**（否则面板无法区分"这个字段它给不了"与"这次取失败了"）。

### 2.6 执行模型（已定 3 + 已定 4：所有插件一样，包安装、不沙箱、每个插件一个常驻子进程）

- **所有插件同一套**：包安装（清单 + 校验 + 启停 + 卸载），**每个插件跑在自己的常驻子进程里**，不沙箱。
  ⚠️ 修正记录：最初讨论过"面板进程内"（同进程）与"一个共享的插件宿主机进程"，两档都**已放弃**。
- **已定 4**：子进程取"**常驻**"（不是每次执行新起一个）—— 插件加载后一直活着，可持有会话与缓存，
  换版本只重启它自己。放弃"每次新起"的理由：每次有几十毫秒启动开销，而元数据是高频调用
  （一次详情要问十几次）。
- **"面板停、插件就停"由宿主保证**：子进程是面板的子进程，面板退出时直接终止它们 ——
  **不依赖插件配合**（这一条比"同进程 + 靠插件自己的 `shutdown` 钩子收进程"更可靠）。
  插件**自己**再起的东西仍要在 `shutdown` 里清理（否则会变孤儿占着端口）。
- **插件内部的事，面板不管**：插件要不要起自己的实例、起几个、监听哪个端口，都是插件自己的逻辑
  （猫源那类"部署实例"的插件自己在内部起实例进程）。面板通过公共端点取结果，不关心背后有几个进程。
- 已知代价（知情接受）：

  1. **进程数即内存**。实测（路由器）：总内存 2.0GB、可用约 590MB；容器内面板 `server.js` 83MB，
     两个源子进程分别 181MB 与 137MB；空转的 Node 进程基础开销约 40~60MB
     （容器入口 `entrypoint.js` 为 49MB）。⇒ 每多启用一个插件就多一份基础开销，重活插件更高。
     **需要一条护栏**（见待定 25）。
  2. **改插件要重启那个插件的进程**（Node 的 `require` 缓存不可卸载）。代价比"重启面板"小得多：
     面板与 Emby 不受影响。管理页上要把"上传 / 启停 / 卸载"与"重启该插件进程生效"绑在一起说清。
  3. 插件之间不能共享（每个进程自己加载依赖），内存与启动时间随插件数增长。
  4. 面板要管 N 个进程（启停、健康、日志、崩溃重启）。这层**不用新造**：现有源那套子进程管理
     （`runner.js`：启动 / 嗅探端口 / 留尾部日志 / 停止）可复用。

- 选择依据（供后来者理解取舍）：**跨进程本身不贵**（常驻进程之间一次调用约 0.1ms 量级，
  远小于一次上游请求的几十毫秒）；贵的是**每次执行新起一个进程**。被放弃的两档与代价见待定 24。

### 2.7 参考：Emby 官方插件的权限与 UI 模型

同类产品的既有做法，可作取舍依据（来源：`dev.emby.media` 的 Server Plugins 文档）。

- **权限：零沙箱、全信任、进程内。** 插件是 .NET 程序集（DLL），放进服务器的 `plugins/` 目录，
  由服务器**在同一进程内加载**。没有权限模型 —— 插件通过依赖注入直接拿到服务器内部接口，
  官方文档点名的包括 `IFileSystem`（读写盘）、`IHttpClient` / `INetworkManager`（联网）、
  `IProcessFactory`（起进程）、`IZipClient`。即"服务器能做的，插件都能做"。
  代价：插件崩溃或卡住会把整个服务器带下去；改完要**重启服务器**才生效。
- **安装与更新：清单 + 校验。** 清单含 `guid`、`name`，`versions[]` 各带 `version`、`targetAbi`、
  `sourceUrl`、`timestamp`、`checksum`；登记一个清单地址即可在线安装与更新。
- **UI：声明式。** 官方明确记录过"让插件自己写 HTML + JS + API 端点"的教训：复杂，且服务器一改、
  插件就坏（视觉或功能）。现行做法是插件只声明配置模型（属性 + 标注），**界面由服务器自动生成**，
  插件无法影响外观。

⇒ 本项目可借鉴：**权限取"不沙箱 + 独立常驻子进程"**（与 2.6 一致）；**设置界面以声明式为主**
（插件声明字段、面板渲染），静态页面只在需要复杂交互时使用；**插件清单参照 Emby 的清单字段**
（含每版本校验和），但保留本项目"网页上传即用"的优势（Emby 需重启）。
⚠️ 一处前提差异：Emby 插件是**编译产物**，发布与安装有门槛；本项目的首页插件是
"贴一段 JS 文本即可运行"，门槛低得多，更像脚本分享。这条差异在讨论中提出过，最终未被采纳为
"分类保留沙箱"的理由（见待定 24 的取舍记录）。

### 2.8 面板与插件之间的通道（已定 5：管道）

- 面板 `spawn` 插件时接一条通道（Node 的 child IPC；非 Node 插件可用"stdin/stdout 每行一条 JSON"）。
- **复用现有实现**：首页插件已经是这个形态（`spawn.js` / `sandbox.js` 的
  `job` / `rpc` / `rpcResult` / `done` 消息），超时、错误回报、日志都在。
- 不占端口、不用鉴权（只有父子能碰）、更快；只有父子能说话（插件的 webui 本来就不靠它 ——
  那是面板托管的静态文件）。
- **插件内部要不要给自己的实例开端口，不受限制**（是插件自己的事，面板不参与分配、也不依赖它）。
- 调试口径：面板把每次请求与回复写进日志（沿用现有源"留子进程尾部日志"的做法）；
  必要时补一个"插件调试台"（在面板里手发一条消息）。
- 被放弃的替代：本地端口 + HTTP（要新造端口分配、冲突处理、残留清理）；Unix socket
  （不占端口号、可 `curl --unix-socket`，但要管路径与残留文件）。端口形态唯一真实的好处是
  `curl` 调试直观，已用日志口径覆盖。

### 2.9 取数式样：一层式与两层式（已定 6 + 已定 7）

**已定 29："线路"是统一的结构 —— 一个名字对应一个地址。**
不管哪类站点（聚合站 / 直查），返回的都是若干条线路；直查那类也**可以有多条**。
⇒ 数据结构上没有两套：**播放项就是"线路（名字 + 地址 + `ref`）"**，一层式与两层式只差
"怎么取到这些线路"（取数链路），不差数据结构。名字由站点给（见已定 30）。

**聚合的粒度是"版本"，不是"站点"**：对某一部片的某一集（一个元数据坐标），面板只做一件事 ——
向所有该域的源插件询问"这一集有哪些可播地址"，能给出的各算一个版本，都不能给就如实空。
在这个定义下，"内部要走四步才答得出"（聚合站那类）与"一步就答得出"（直查那类）**对面板是同一件事**。

**已定 13：式样、播放项与"解析地址"都是「按注册的站点」的粒度，不是"按整个源插件"。**
一个源插件可以注册多个站点，各站点的式样可以不同（有的站点是聚合站 → 两层式，有的是直查 → 一层式）；
播放项归属于具体的站点，解析地址也按站点归属。⇒ 面板的调用目标始终是**站点**，插件只是站点的提供方。
（早先几轮把粒度写成"源插件"，此处统一改为"站点"。）

**已定 12：面板侧"线路结果"的缓存判据 = 只要有线路就存**，不要求"所有站点都通"。
理由：要求"全站都通"太苛刻 —— 一个慢站或一次抖动就会让整份结果进不了缓存，
而用户看到的是"每次点开都慢"。缺的那几条线路由日志点名（沿用早已定下的口径）。
⇒ 早先记过的"缺线路的结果会被钉住"这一顾虑，按下这个口径收起来，不再作为反对理由。

差别在**取数链路**，因此由站点申报式样（**已定 6**）：

| 式样 | 链路 | 面板在中间做什么 | 适合 |
|---|---|---|---|
| **两层式** | 给词 → 候选列表 →（面板打分 / 过滤）→ 取选中那条的播放项 | 打分与过滤 | 聚合站那类（返回的是候选，不挑就会拿错同名片） |
| **一层式** | 给词 → 直接回播放项列表 | 不做筛选（插件自己保证取准） | 直查那类（给关键词就出地址） |

**打分与过滤留在面板、不搬进插件（已定 7）**，理由：
① 职责切分本来就是"聚合负责过滤、逻辑归插件"（见 2.3）；
② 它是**跨来源统一的判据**（`match.js` 是"这是不是目标作品"的唯一实现，见 ADR-0003）——
搬进插件会让判据分叉，同名错片会重新出现；
③ 它还牵着一串只属于面板的概念（分数线、最多留几条、没拿到时再往下打几条、匹配到底）。
⇒ 于是"能力申报"实际就是一句：**这个插件支不支持候选式**。

⚠️ **聚合参数只对两层式插件有效**。一层式插件不看分数线、条数、补打 K ⇒ 设置页必须说清
"哪些参数对哪些插件生效"，否则会出现"调了没反应"。

### 2.10 播放地址的转交（已定 8 + 已定 9 + 已定 10）

播放项里给客户端的地址是**面板的地址**（形如 `http://<面板域名>:<面板端口>/…/<ref>`），
面板收到请求后通过管道把 `ref` 转给插件，插件回一个**真实可直连地址**，面板 **302** 过去
（与 ADR-0006 一致：面板不扛流量）。客户端感知不到插件，也不需要知道插件在哪。

- **已定 8：host 必须是面板，不能是插件自己开的端口**。客户端要能访问那个地址，而
  **面板的端口是已发布、确定可达的**；插件的端口没有发布（现状里"源端口没发布"就导致过配置中心打不开）。
  把 host 定成面板，等于把现有链路里的"解析坐标"那一步从面板挪进插件 —— 现状是面板解析
  `MediaSourceId` 里的 base64 再 302，新形态是面板把 `ref` 原样转给插件、插件回地址。
- **已定 9：只做 302，需要代理的先不做**。插件给出可直连地址 ⇒ 面板 302。
  插件若说"必须带 header / cookie 才能播" ⇒ **如实回"该源需要代理，暂不支持"**，不静默失败。
  被放弃的两条替代（供后来者查）：面板破例做代理（会推翻 ADR-0006：带宽、超时、断点都要管）；
  插件自己代理（那个端口要能被客户端访问 ⇒ 得自行发布）。
- **已定 10（再修订）：两级缓存，各管一段。**
  - **插件侧**：插件把它自己的详情缓存在**自己的数据目录**里，管"同一部片下次点开也快"。
    缓存什么、多久、何时失效，全由插件决定（面板不干预）。这也是**插件的义务**（见下）。
  - **面板侧**：只缓存**这一条目的线路结果**（面板聚合出来的那份），**不做"完整快照"**。
    它的 `key` 里带上**所有影响结果的参数**（打分参数、线路过滤、模板、站点集合……），
    于是"参数一改、key 就变、旧结果自然失效"，不需要人工清缓存。
  - **已定 32：面板侧这份缓存的有效期按天算，默认 1 天**（设置项保留，可改）。实际效果：
    同一部片当天再点开是毫秒级（不必问插件）；它的 key 带上所有影响结果的参数，
    **改了参数 key 就变、旧结果立即失效** ⇒ 不会出现"改了参数还在用旧结果"。
    ⚠️ 代价如实记着：一次**缺了几条线路**的结果会留在缓存里最长 1 天（抖动的影响比"秒级有效期"长）。
    既定的口径是"**有线路就存**"（已定 12），所以这一条属于知情接受。
  - ⚠️ 前提写成义务（不是可选项）：**插件应当自己缓存，把常见查询做到秒回**。
    因为面板侧那份缓存只挡几秒内的连问，**超出之后的热度全压在插件身上**。
  - ⚠️ 配套：**面板要按插件记录每次聚合的耗时**（日志 + 统计），否则"慢插件"查不出来，
    用户只会感觉"面板又慢了"。现有按站点的测速统计可延伸到按插件。
  - **慢插件由超时兜住**（与现状的单站超时同理）：超时只把上限钉住，差别在"这份代价多久付一次"。
  - 配套机制在新架构下的落点：**站点级超时**与**失败跳过**都改成"按插件 / 按注册的站点记账"，
    现有那套 `shouldSkip`（最近一次请求失败 → 跳过一段时间 → 到期自动重试）逻辑照搬即可。
  - **义务写成一句**：**`ref` 必须可被重复解析** —— 只要内容还在，插件随时能用它换出地址。
    不写清楚，出事时归因不明（是插件没做到，还是面板不该缓存）。
  - 顺带：播放那一跳要快也是**插件的实现义务**（内部缓存或预热），面板帮不了。
  - 同一条原则对**元数据插件**一样适用：它的响应缓存也归它自己（面板侧同样只留短期的那点）。

### 2.11 元数据插件要提供什么（从现有上游用量倒推）

做法：把面板现在从上游取用的东西列全，那就是元数据插件契约的最小集合。**面板要什么，插件就提供什么**。

**四个动作**

| 动作 | 用途 |
|---|---|
| 取元数据（单条） | 条目详情、列表条目、播放页需要的一切 |
| 取一季分集 | 季 / 分集列表、`NextUp`（下一集）、总集数 |
| 搜索 | 客户端搜索框（`SearchTerm=`）走这条 |
| 注册 | 申报域 id、能力清单、Id 形状声明 |

**"取元数据"里现在确实被用到的字段**（按用途分组）

- **身份**：条目 id、类型（电影 / 剧集）
- **名字与时间**：主标题、原始标题、年份、首播日期
- **给源插件的搜索用词**（现为 `searchTitle`：主标题没中文时回退中文别名）← 见待定 31
- **简介**（有长度上限）
- **图片**：海报、背景（+ 图集，详情页用）
- **分类**：类型名列表 **与带 id 的类型项**（客户端要能点进"类型"，只给名字点不进去）
- **规模与评分**：季数、评分
- **详情页那一批**（现为同一次请求的 `rich` 附加）：标语、状态、时长、分级、制作公司（**必须带 id**）、
  制片国家、关键词、外部 id（imdb / tvdb / wikidata）、预告、演职、相似推荐

**"取一季分集"里被用到的**：集号、集名、简介、首播、剧照、评分、时长（拿不到时如实留空）

**⚠️ 不属于插件、别塞进来的**：图片的**代取与签名**（面板为客户端取图，见 ADR-0013）、
各类缓存（各自管各自的，见 2.10）、Emby 的 DTO 形状（面板负责转换，见 2.5）。

**Id 的拼装与解析**：见 2.1 末与已定 14 —— 形状由面板统一，插件只给条目 id + 剧集式/电影式。

### 2.12 模板与域（已定 20 + 已定 31）

- **已定 31：模板就是一份配置数据文件**，内容 = **选中的站点 + 打分过滤参数**；
  **它自己的 id 就是这套模板的身份**（随机生成、之后固定）。
  ⇒ 打分与过滤**逻辑**仍在面板（已定 7），但**参数跟着模板走** —— 不同域因此可以有不同的
  分数线 / 留几条 / 补打 K / 线路过滤。
  ⚠️ 其中只有一部分参数对**一层式**站点有意义（它们不做筛选）⇒ 设置页仍要写清"哪些参数
  只对两层式站点生效"，免得出现"调了没反应"。

- **每个域最多一个模板**（域 → 模板 是一对一）。理由：模板本来就是按需求配好的，一个域挂多套
  必然出现重复，维护起来也说不清"这次到底用了哪套"。⇒ 不做"默认模板"、不做"多模板取并集"那套。
- **一个模板可以被多个域共用**（域 → 模板是多对一，不冲突）：模板只是"一批站点"，不必唯一归属。
- **同一个站点可以出现在多个模板里**，但站点表上要能看出"它被哪几套模板用了" ——
  否则以后查不清"为什么这个域用了这个站"。

### 2.13 插件的 webui 与设置怎么落地（已定 21 + 已定 22 + 已定 23）

- **已定 22：插件的设置「声明归插件、存储也归插件」**（都存在插件自己的数据目录里）。
  收益：面板"清空插件数据"就是**删那个目录**，干净、无第二套存储。
- **已定 21：面板侧那条通道是「纯转发」**。因为存储与字段都归插件，面板**不解析、不存储、不校验**。
  链路：webui（浏览器里的页面，只能发 HTTP）→ 打到**面板**（同源）→ 面板按路径里的
  「插件类型 + 插件 id」把请求**通过管道转给插件** → 插件处理并写自己的目录。
  ⇒ 插件想怎么设计自己的接口都行，面板永远不必跟着插件改。
  面板要做的只有两件小事：① 一条转发通道（如 `/api/plugins/<类型>/<id>/…`）；
  ② 入口的声明（见 2.4 与下面的 LuCI 参考）。
- **已定 23：插件 webui 的托管路径与转发通道都必须受门禁**。
  ⚠️ 现状是**静态文件不需要登录**（门禁只拦 `/api/**` 与 `/website*`）——
  若把插件 webui 放进静态目录，不登录就能打开它的设置页。
- 顺带：面板**不需要知道**"插件设置改没改、要不要重载" —— 那是插件自己的事。

### 2.14 参考：LuCI 插件怎么注册它的 web UI

（来源：OpenWrt LuCI 仓库 `applications/luci-app-example` 的实际结构，可作借鉴。）

**包内布局**（包里的 `root/` 对应装到设备根）：

| 路径 | 作用 |
|---|---|
| `/usr/share/luci/menu.d/luci-app-xxx.json` | **菜单声明** |
| `/usr/share/rpcd/acl.d/luci-app-xxx.json` | **权限声明**（能调哪些接口；不对就 "Access denied"） |
| `/www/luci-static/resources/view/xxx/*.js` | **前端页面** |
| `/usr/share/rpcd/ucode/xxx.uc` | 后端 RPC |
| `/etc/uci-defaults/80_xxx` | 首次安装时创建默认配置 |

**菜单声明的实际形状**：

```json
"admin/example/form": {
  "title": "Form View",
  "order": 1,
  "action": { "type": "view", "path": "example/form" }
}
```

父节点用 `"action": {"type": "firstchild"}`；还可以写 `"depends": {"acl": ["luci-app-example"]}`。

**设置存哪**：`/etc/config/xxx` —— **插件自己的配置文件**，schema 由插件自己定，LuCI 不认识这些字段。

**卸载**：菜单是**扫 `menu.d` 目录发现**的，没有中心注册表 ⇒ 删包时文件一起没 ⇒ **菜单项自动消失**。

**可借鉴三点**：
1. **入口是"文件声明 + 宿主扫描"**，不需要"注册"动作 —— "注册了 webui 就加导航"落地就是
   扫插件目录里的一个声明文件（给显示名、排序、指向哪个页面）。
2. **设置由插件自己存自己管** —— 与已定 22 一致（LuCI 这边就是那个 `/etc/config/xxx`）。
3. **权限要显式声明** —— 对应到本项目就是"这些页面要登录才能看"（已定 23）。
   本项目不沙箱，所以不限制"插件能做什么"，只限制"谁能打开它"。

## 三、公共端点（已定 16）


**源插件**（已定 16）

| 动作 | 入参 | 出参 | 必需性 |
|---|---|---|---|
| 站点清单 | — | 站点数组（含站点级能力申报） | 必需 |
| 候选 | 搜索词、页码 | 候选列表 | **仅两层式站点**（见 2.9） |
| 取播放项 | 站点坐标（+ 搜索词） | 播放项列表，每项 = 面板地址 + `ref` | 必需 |
| 解析地址 | `ref` | 真实可直连地址 | 必需 |
| 站点测速 | — | 该站点的连通性与耗时 | 必需（已定 15，本次实现） |
| webui | — | 静态文件（插件设置页） | 可选 |

**元数据插件**（已定 16）：**动作与"面板从上游取用的东西"一一对应**（见 2.11）

| 动作 | 入参 | 出参 | 必需性 |
|---|---|---|---|
| 注册 | — | 域 id + 能力清单（即 2.11 那张字段表：它会哪些、缺哪些）+ 剧集式 / 电影式 | 必需 |
| 取元数据 | 条目坐标（一次一个，见待定 4） | 规范字段（2.11 列的那批）+ 成败 | 必需 |
| 取一季分集 | 条目坐标 + 季号 | 分集列表（集号 / 集名 / 简介 / 首播 / 剧照 / 评分 / 时长） | 必需 |
| 搜索 | 搜索词 | 候选列表 | 必需 |
| 首页内容 | 域 + 行 | 行 | 见**待定 5** |
| webui | — | 静态文件 | 可选 |

要点：**"播放"的职责收窄成"解析地址"**，而原来的"详情"变成"取播放项"。
一层式与两层式在"解析地址"这一步**完全一致**（`ref` 由插件自己编，面板不解析）。
两条链路在契约里的落点：
- 两层式：候选 →（面板打分 / 过滤）→ 取播放项 → 解析地址
- 一层式：取播放项 → 解析地址

**已定 19：只保留「站点测速」一个动作，它同时承担"通不通"与"快不快"。**
不另设"探测"动作 —— 插件的**站点探测逻辑**注册成这个测速端点即可。
⇒ 于是分工是：**站点清单 = 静态声明"这个插件有哪些站点"；站点测速 = 实测"这个站点能不能用、多快"**。
（早先"探测并入站点清单"的说法作废：可用性由测速端点回答，不再靠"清单取不到"来判断。）

**命名用动作名**：走管道之后没有"网址"了，端点名就是**一个动作标识**。对比：
现状是 `POST http://<源地址><站点 api>/search { wd, page }`；新形态是
`{ action: 'search', site: …, wd, page }`。⇒ 用动作名（`站点清单` / `搜索` / `取播放项` / `解析地址` / …），
不写成 `/config`、`/search` 那种路径样式，免得后来者以为还要发 HTTP。

24. ~~权限模型~~ **已定 3**：见 2.6 —— 所有插件一样（包安装、不沙箱、**每个插件一个子进程**）。
    以下为取舍记录，供后来者理解为什么放弃其他两档：

    - **面板进程内（同进程）** —— 放弃理由：① 同步死循环无解（堵住事件循环，面板与 Emby 端点
      一起卡死）；② 改插件要重启面板，"上传即用"消失；③ 内存泄漏只能靠容器重启复活；
      ④ 插件可直接 `process.exit()`、可改全局对象，护栏无效。
      （已有的缓解：`uncaughtException` / `unhandledRejection` 是"记录 + 继续跑"，抛异常不带走面板。）
    - **一个共享的插件宿主机进程** —— 放弃理由：隔离粒度太粗（一个插件闹腾影响同一宿主机里的
      其他插件），且"重启换版本"要连累同宿主机上的其他插件。
    - **沙箱档（分类保留）** —— 放弃理由：① **沙箱与"逻辑归插件"存在根本张力**：沙箱禁止插件联网，
      所有上游请求就得由宿主代做，宿主于是必须懂"怎么请求上游"，而"怎么请求上游"正是要搬进插件的逻辑；
      ② 元数据是高频调用，每次执行新起进程的开销不划算。
    - **不沙箱的共同前提**：面板进程在容器内是 `root`，数据卷挂 `/data`，
      其中含 `auth.json`（面板登录凭据）、`settings/`（含上游 token）、`emby/`（客户端账号库）。
      ⇒ 不沙箱的插件对**面板的一切**可见，并可对外发送。容器本身是一层边界
      （实测：非特权、bridge 网络、只挂 `/data`），宿主路由器不在它的直接射程内。
25. ~~插件进程的护栏~~ **已定 28：不硬设数量上限，但把内存占用显示出来**。
    进程数即内存（实测数据见 2.6），所以**概览页要显示每个插件进程占多少内存**，
    涨了能看见；不用"超限就拒绝启用"那种硬拦。
26. ~~子进程的两种变体~~ **已定 4**：取"每个插件一个**常驻**子进程"（见 2.6）。
27. ~~面板与插件之间走哪条路~~ **已定 5**：取"管道"（见 2.8）。
28. ~~播放坐标由插件给出、面板原样回传~~ **已定 8 / 9 / 10 建立在此之上**（见 2.10）：插件在"取播放项"里返回的每个播放项
    带一个**插件自己定义的坐标串**，面板不解析、只保存，客户端点播放时原样传回"播放"端点。
    这样"条目 → 线路 → 集 → 地址"（猫源那类，四层）与"条目 → 地址"（直查那类，两层）都能表达，
    面板不必理解层级。代价：面板不再自己拼播放坐标，依赖插件提供。
30. ~~只有一个播放项时，版本名由面板起默认名~~ **已定 30：改成"播放项必须自带显示名"**。
    更正早先的表述：名字**一直都有**，来源是源给的线路名，面板拼成 `${站点标签} · ${线路名}`
    （加站点标签是因为多站之间线路名会重名，不加以分不清）。
    真实的问题只是：**直查那类站点没有"线路"这个层级，名字那格没人填**。
    ⇒ 契约要求：**"取播放项"返回的每一项必须带一个显示名**（聚合站 = 线路名；
    直查那类由它自己决定，例如片名 / 集号 / 站点名）；**面板只负责把它传到客户端，不起名、不编**。
    站点真的想不出名字 ⇒ 如实留空，面板不兜底。
30. ~~每个源插件至少申报一个"站点"~~ **已定 17**：**站点数不管，0 个也可以** ——
    报 0 个的插件在站点表 / 模板里就不出现（等于用户用不到它，如实如此）。
    ⇒ 想让自己的插件被用，就申报站点，这是插件作者自己的选择，面板不强制。
31. ~~搜索用词由元数据插件给出~~ **已定（并入 2.11 的字段表）**：面板现在的链路是"拿元数据里的**片名**去搜源"，
    而按编号 / 关键词检索的源用片名搜不到。⇒ 契约需允许元数据插件提供"给源插件搜索用的词"
    （片名只是其中一种，也可以是编号、别名、标签）。缺这条，那类内容连搜索这一步都走不到。

    打分与过滤留在面板 **已定 7**（见 2.9）。
33. ~~缓存的前提~~ **已定 10（再修订）**：见 2.10 —— **两级缓存**：插件侧缓存它自己的详情（管"下次点开也快"）；
    面板侧只缓存"这一条目的线路结果"且**有效期很短**（挡掉客户端一次播放连问三遍）。
    面板侧缓存的 key 带上所有影响结果的参数 ⇒ 参数一改自然失效。

    （新代码不读；用户自己重新设置）。丢弃范围见待定 37。

    - **可丢（配置类）**：`panel.json` 的缓存设置、`agg.json` 的站点勾选与打分参数（模板制下要重勾）、
      各缓存库（`cache/` 下的详情快照与元数据缓存，本来就是可丢弃数据）。
    - **⚠️ 按"全新安装"的口径，以下也会重来**：`emby/emby.db` 里的**客户端账号与观看进度** ——
      别人的客户端要重新登录，"继续观看 / 已看"全部清空；已安装的**源包与其部署实例**（`sources/`）要重装。

## 五、推进顺序（草案）

1. **前缀分派改为查注册表**：把"认哪个前缀"从硬编码域换成查注册表。纯重构，外部行为不变。
2. **模板**：站点集合 + 归属域。
3. **插件管理页 + 导航挂载**：清单、包安装（tar.gz + 两道 md5）、启停、卸载、状态可见；
   插件 webui 上栏（入口由插件的声明文件扫出来；设置声明与存储都归插件，见 2.13）。
4. **源插件化**：先抽公共端点接口 + 一个猫爪实现（编译期注册，行为不变）；再让它可安装。
5. **元数据插件可安装**。

## 六、明确不做

- **不改 Emby 层的条目 Id 方案**（`{域}_{编号}_{tv|movie}[_s{n}][_e{m}]` 保持不变）——客户端手里的
  继续观看、进度库的键、首页插件的条目契约、详情快照的键都挂在它上面。
- 不引入自动推断类的启发式：域归属、站点归属一律由**声明或选择**决定，不猜。
