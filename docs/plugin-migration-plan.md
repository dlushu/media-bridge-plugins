# 插件化改造：施工批次计划

- 状态：**计划**（随进度更新；改完的批次在这里打勾并记下验证方式）
- 依据：[plugin-contract.md](https://github.com/dlushu/MediaBridge-plugin-devkit/blob/main/framework/contracts/plugin-contract.md)（契约）· [adr/0028](https://github.com/dlushu/media-bridge-panel/blob/main/docs/adr/0028-plugin-system.md)~[0034](https://github.com/dlushu/media-bridge-panel/blob/main/docs/adr/0034-fresh-install-no-migration.md)（决策）
- 讨论存档：[plugin-arch-draft.md](plugin-arch-draft.md)

> 本文讲的是**面板仓库**的改造过程：文中出现的 `server/`、`public/`、`docs/` 等路径都指面板仓库
> （[media-bridge-panel](https://github.com/dlushu/media-bridge-panel)）；插件源码现在住在本仓库的 `plugins/`。

## 一、两条总原则

1. **批次是"开发与验证的顺序"，不是"发版顺序"。**
   按 [ADR-0034](https://github.com/dlushu/media-bridge-panel/blob/main/docs/adr/0034-fresh-install-no-migration.md)，本版当作全新安装、不留兼容分支 ——
   所以中间批次**不对外发版**，一次性把整套做完、发一个大版本。
   若改成"每批都发版"，就需要额外的兼容策略（与"不留兼容"相抵），不建议。
2. **能做成纯重构的批次，先做成纯重构**：外部行为一字不变，用"改动前后同一批请求的响应逐字对比"
   来证明没改坏。做不到"行为不变"的批次，要在计划里写明它变了什么、怎么验。


### 缓存落点（改造后各库归谁）

| 库 | 内容 | 归谁 | 位置 |
|---|---|---|---|
| `lines.db` | 这一条目的线路结果（面板聚合出来的那份） | 面板 | `cache/` |
| `sitestat.db` | 站点统计与测速（按插件 + 站点记账） | 面板 | `cache/` |
| 元数据响应缓存 + 名字索引 | 上游响应缓存、名字 → 搜索结果 | 元数据插件 | `plugins/metadata/<id>/data/` |
| `image_index` | 图片索引 | emby 层（它服务的是图片端点） | `emby/cache.db`（不动） |
| 插件自己的取数缓存 | 各插件自己定 | 插件 | `plugins/<类型>/<id>/data/` |

### 这份树里已确认的四处

1. **内置插件随包发行**：仓库里 `plugins/` 放内置插件源码，开机同步进 `data/plugins/`
   —— 否则"全新安装"之后面板是空的（连元数据都没有）。先例：现在的内置首页示例就是这么同步的。
2. **`server/modules/source/` 并入 `server/modules/plugin/`**：
   它那套"下载包 / 起进程 / 端口 / 自动更新"现在要用在**所有插件**上，已经不是"源"专有。
3. **超时与并发进模板**；**测速的结果值是面板级共享的一份**（不跟模板走），
   **测速的开关与间隔放面板设置**。⇒ 于是原来「站点与参数」+「聚合参数」两页合成模板页，
   测速那两项挪去面板设置。
4. **图片索引留在 `emby/cache.db` 不动**（按 ADR-0011 的"按消费方分库"，
   它服务的是 emby 那侧的图片端点），不跟着元数据走。

## 三、通用验收口径（每批都要过）

- `npm run check`（文风 + 语法门禁）。
- **本机起实例**：`DATA_DIR=<临时目录> WEB_PORT=<端口> node server.js`，用浏览器逐页打开相关页面
  （前端改动必须真开一遍，不能只看代码）。
- **回归对比**：行为不变的批次，抓同一批端点（详情 / 季 / 集 / 图片 / 播放 / 首页）的响应，
  与改动前**逐字对比**。
- **路由器实测**：涉及部署形态的批次，按现有手法打进去、重启应用进程、验收后再决定去留。
- 每批完成后：把结果补记到本文对应小节，并同步受影响的文档。

### 批次 4 — 源插件化：整套搬进猫爪插件 · 已完成

**范围**（本批开工时定下的口径）：不只是把协议搬走，**连源实例本身一起搬** ——
猫爪插件自己存实例清单、自己下载与起实例进程、自己管自动更新与配置中心入口；
面板不再认识任何"源地址"。依据见 [plugin-contract.md](https://github.com/dlushu/MediaBridge-plugin-devkit/blob/main/framework/contracts/plugin-contract.md) 第十五节
与 [plugin-arch-draft.md](plugin-arch-draft.md) 第 82~83 行（"插件内部起几个实例、监听哪个端口，是插件自己的事"）。

**为什么一次搬完而不是分两步**：分两步会留一个"面板仍托管实例、只把协议转给插件"的过渡态，
那个过渡态里两套实例清单并存（面板的 `sources.json` + 插件的），反而更容易配错。
一次搬完，实例清单只有一个来源。

**做什么**

1. 新增 `plugins/source/<id>/`：契约里那五个动作 + 自带 webui。
   包内自带取数所需的一切（HTTP 客户端、`/config` 摊平、下载器、实例进程管理、自动更新），
   **不 require 面板任何代码**（插件是独立包，面板升级不该牵着它）。
2. 面板删除源层：`server/modules/source/` 整个模块（下载 / 起进程 / 端口 / 自动更新 / 配置中心代理），
   `server/core/catpaw.js`（协议搬走；其中 `normName` 是**面板侧的打分知识**，归 `agg/match.js`），
   `/api/sources*`、`/api/run*`、`/api/base*`、`/website*` 与 `server.js` 的配置中心兜底转发。
3. 聚合层四处协议调用改成插件的动作：`/init`（并入插件的"候选"内）、`/search`、`/detail`、`/play`。
   新增 `agg/source-bridge.js` 作为唯一的转接处 —— 它把插件的回复**还原成上游那份形状**
   （`{ status, ok, text, json }`），所以 `service.js` 里那套 404=无结果、超时文案、逐站记账
   一个字都不动。这是本批"行为不变"的关键手法。
4. 站点清单的来源从"面板自己去问每个源的 `/config`"改成插件申报（本属批次 5，
   因为实例已经归插件、面板再也够不到那些地址，只能一起做）。

**行为变化（如实列出）**

| 变了什么 | 说明 |
|---|---|

**过程中发现并修掉的三处（都不在计划里，但都是真问题）**

1. **插件换包会把 `data/` 清空**（批次 3 留下的）：`installDir` 覆盖时先 `rmSync` 整个插件目录，
   `copyDir` 那句"跳过 data"只保证不复制、不保证不删 —— 实测把刚加好的实例清单清掉了。
   已改成"先把 `data/` 挪到一边、换完再挪回来"。
2. **宿主重启插件会有竞态**：`restart()` 只等 300ms 就 `start()`，而 `start()` 看到旧进程还在会直接返回
   —— 插件自己的善后逻辑越认真（退出越慢），越容易"停掉了却起不来"。已改成**等进程真的退出**再起。
3. **端口被抢会被误判成"起来了"**：两个实例配到同一个端口时，后起的那个的"端口通了"其实是前一个在答，
   于是顶着别人的站点装成自己（站点身份会张冠李戴）。已在 `host-boot` 里加了"启动前先看端口"，
   如实失败并说清原因。

**这一批没做（按计划留给后面）**：`解析地址` 收 `ref`（批次 7）、播放地址不再由面板改写（批次 7）、

文档还写着它们，先在计划里挂账）。

### 批次 7 — 播放地址转交（`ref` 由插件解析）· 已完成，待确认

**已定的形态**（把契约第五节那两行落成具体做法；依据是契约第九节"`ref` 由插件自己编，面板不解析"
+ ADR-0030）：

1. **线路与选集的解析搬进源插件**：`$$$` / `#` / `$` 是**猫爪源自己的约定**
   （直查那类插件根本没有线路），所以由插件把 `/detail` 的原始文本解析成
   「线路 → 选集」；面板不再解析。
   ⚠️ ADR-0033 说的"打分与过滤留在面板"指的是**候选筛选**（`match.js` 那套"这是不是目标作品"），
   与线路解析是两件事，别混。
2. **`ref` 由插件编**：`取播放项` 回的结构里，每个播放项带一个**面板不解释**的 `ref`
   （插件自己决定里面写什么、自己保证可重复解析）。
3. **面板只做 302**：`MediaSourceId` 里带 `ref`（不再带"源/站点/线路/集"那套坐标）；
   播放时面板把 `ref` + **客户端访问用的主机名**交给插件，「解析地址」回来什么就 302 到什么。
   客户端主机名要一起给出去 —— 本地部署的实例回的是回环地址，插件要拿它拼成"客户端够得着"的地址
   （现在这一步是面板在做，见 `emby/service.js` 的 `redirectUrl`）。
4. 由此**两处过渡态一起收口**：`站点清单` 不再需要 `url`/`port`；面板不再需要知道实例端口。

**保留在面板的**：打分与过滤（`match.js`）、线路过滤规则（`lineFilter`，只匹配线路名）、
集名里的规格解析（`parseEpisodeMeta`，那是填 Emby DTO 用的）、以及拼 `MediaSources` 那整套。

**动到**：`plugins/source/<id>/`（新增线路/选集解析 + `ref` 的编解 + 「解析地址」按客户端主机名回地址）；
`agg/service.js`（`fetchDetailOnce` 变成"调插件取结构化结果"，`playEpisode` 传 `ref` 与客户端主机名）；
`agg/source-bridge.js`（透传新字段）；`emby/service.js`（`catpawSourceId` 的载荷、`redirectUrl` 的去留、
`MediaSources` 的构造）。

**验证（已做）**：本机起实例 + 假源（它的 `/play` 故意回**回环地址**，正好验地址改写）——
用真 Emby 账号拿 token，客户端真走的那条端点（`…/videos/{ItemId}/stream.mkv?MediaSourceId=…`）实测：
- 详情里每条线路的每个播放项都带 `ref`（形如 `catpaw/eyJz…`，面板不解释它）
- 302 的 `Location` = **客户端够得着的地址**：本地部署的实例把回环换成客户端域名、端口原样保留
  （`http://127.0.0.1:9999/…` → `http://192.168.1.100:9999/…`）；**外部地址的实例原样不改**

**顺带修掉一个真问题（不在计划里）**：源回的地址里含中文站名时，`Location` 头会被 Node 直接拒发

  - 同一请求连问三遍 → **只打一次插件**（`search` / `detail` 各 1 次），第二、三遍命中缓存，日志写"没打插件"；
  - 改一条影响结果的参数（分数线）→ **立即换 key、重打插件**（各 +1）；
  - **缺线路仍缓存**（B 站搜不到、A 站有能用的线路）→ 照存，日志点名"⚠️ 但不完整：1 个源没搜到（站B）"，
    第二遍命中缓存不打插件；
  - 一条能用的线路都没有（定位不到这一集）→ **不存**（ADR-0025 的边界：`usable > 0` 才存）；
  - 命中缓存时响应里**没有** `sites[].data`（现算那次有）—— 刻意（那份上游原样响应不入库，见 `slimLines`）；
  - `agg_stat` 按插件记到（`aggStats()` 回 `{catpaw:{ms,sites,at}}`）。
- **没验到的（如实记）**：**没在同一条真源上跑过三连问**（本机没有可用的猫爪源实例）——
  上面的口径是**打桩** `source-bridge` 验的，链路是面板侧那一段。插件侧的落盘缓存
  （`plugins/source/<id>/lib/cache.js`）只过了 `npm run check` 与代码复核，**没在真源上实测过命中**。
  面板「设置 → 缓存设置」页**没能用浏览器逐页验**：这台机器上 WebView 一直未就绪、资源 `net::ERR_ABORTED`，
  连换两个浏览器实例都一样。已核对到的是：模块能被正常服务（HTTP 200）、新增标识符无"用了没定义"、
  console 无 JS 报错。下次有实机条件时，这两条要补上。
- **风险**：中。缓存键少一项就会"改设置不生效"，多一项会无谓失效率 —— 所以 `pick` 与两档超时都进 key。
- **依赖**：批次 6。
